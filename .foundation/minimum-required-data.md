# Minimum Required Data
## Версия 1

---

### 1. Назначение документа

Minimum Required Data (MRD) — фильтр против разрастания продукта.

Документ отвечает на вопрос:

**Какие данные действительно нужны, чтобы ответить: «Какой официальный продукт соответствует этому объекту?»**

Задача MRD:

- защитить OSA от лишних полей;
- не допустить сложные формы «на всякий случай»;
- сохранить простой и спокойный UX для дизайнера;
- связать каждый запрос данных с улучшением качества решения.

Если поле не повышает качество решения для спецификации — его нет в обязательном вводе.

MRD подчиняется Конституции OSA, Единому словарю и логике Decision Engine.

---

### 2. Принцип минимального ввода

Сначала пользователь вводит только минимально необходимую информацию.

Каждый следующий вопрос появляется только тогда, когда без него невозможно повысить качество совпадения / спецификации.

Правила:

1. Начинаем с малого.
2. Анализируем то, что уже есть.
3. Спрашиваем дополнительно только если неопределённость мешает решению.
4. Не превращаем старт работы с объектом в анкету.

Пользователь не заполняет повторно то, что система уже знает.

---

### 3. Первый уровень данных

#### Минимальный набор

- **Изображение объекта интерьера** — достаточный вход для визуального понимания и старта decision path.

#### Почему этого достаточно для первого анализа

На первом уровне OSA не обязан знать производителя, артикул или бюджет.

Ему нужно:

- увидеть объект;
- сформировать профессиональное понимание (Vision);
- дать честный следующий шаг (поиск / HITL / отказ).

Первый уровень обслуживает главный вопрос Decision Engine. Он не обслуживает полный проект, склад или CRM.

---

### 4. Второй уровень данных

#### Состав второго уровня

- **Производитель / каталог** (`manufacturer_id` / URL каталога) — когда нужно направить поиск на официальный источник.
- **Язык / режим анализа** — если влияет на вывод для пользователя.
- [Требует дальнейшего заполнения] Точный обязательный список второстепенных полей UI (placement, overrides и др.) — зафиксировать совместно после стабилизации единого UI→Office сценария.

#### Когда спрашиваем

- Когда без привязки к производителю нельзя честно получить официальную карточку.
- Когда одно уточнение заметно снижает неоднозначность.

#### Когда не спрашиваем

- Когда изображение уже позволяет дать честный итог или честный HITL.
- «На всякий случай» до старта анализа.

---

### 5. Третий уровень данных

#### Состав третьего уровня

- Подтверждение / выбор человека среди кандидатов.
- Human overrides после HITL.
- Данные полного проектного контура (мультиобъект, клиентское согласование, BIM) не входят в текущие границы OSA.

#### Смысл третьего уровня

Третий уровень появляется **после** перехода к следующему этапу жизненного цикла решения, а не на старте.

---

### 6. Что НЕ спрашиваем заранее

- Полную анкету проекта «для будущего».
- Данные, нужные только для отчёта или внутренней красоты системы.
- Повтор уже известных полей.
- [Требует дальнейшего заполнения] Полный негативный список полей — расширить после UX-проработки единого сценария.

---

### 7. Закон постепенного сбора данных

1. Сначала изображение.
2. Затем только то, без чего нельзя повысить качество официального совпадения.
3. Затем подтверждение человеком при необходимости.
4. Никогда — полный опросник до первого полезного итога.

---

### 8. Проверка через Три «У»

#### Принцип минимального ввода

Ускоряет старт, упрощает действие, снижает стресс от форм.

#### Первый уровень данных

Один понятный вход — изображение объекта.

#### Второй уровень только по необходимости

Не превращает анализ в анкету.

#### Третий уровень только после перехода к следующему этапу жизненного цикла

Человек включается, когда это реально улучшает решение.

#### Запрет лишних данных заранее

Защищает от расползания продукта.

#### Закон постепенного сбора

Соответствует минимально достаточной архитектуре Конституции.

---

### Итог

Минимум OSA для старта решения по объекту — **изображение**.  
Всё остальное запрашивается только если повышает качество проверяемой спецификации.

---

Статус: частично заполнен. Состав второго/третьего уровней и полный негативный список полей требуют совместной проработки с человеком.
